# Deploying Homesika to Render

`render.yaml` in the repo root is a **Render Blueprint**: one file that describes every piece
Render must create. Staging is first; production is a copy with live keys, made when you are
ready to launch.

| Render resource | What it runs |
|---|---|
| `homesika-staging-api` (web service, Docker) | Django API + WebSockets (Daphne), at `https://homesika-staging-api.onrender.com` |
| `homesika-staging-worker` (background worker) | Celery: reminders, receipts, reconciliation, provider calls |
| `homesika-staging-beat` (background worker) | Celery beat: the scheduler (always exactly one) |
| `homesika-staging-db` (PostgreSQL 16) | All data |
| `homesika-staging-redis` (Key Value) | Job queues, cache, WebSocket messages |
| `homesika-staging-web` (static site) | The React dashboard |

## One-time setup

1. **Push the repo to GitHub** (`gintason/homesika`).
2. **Create a Render account** at render.com and sign in with GitHub. When asked, give Render
   access to the `homesika` repository only.
3. In Render, choose **New → Blueprint**, pick `gintason/homesika` and branch `main`. Render
   reads `render.yaml` and shows the list of resources above.
   * If it shows an error about a field, copy the message to me. The file is marked
     `TODO(verify)` because Render's docs weren't reachable from my build environment.
4. **Fill in the secrets Render asks for** (those marked `sync: false`):
   * `FIELD_ENCRYPTION_KEYS`: run this on your Mac and paste the output:
     `python3 -c "import os,base64;print(base64.b64encode(os.urandom(32)).decode())"`.
     **Keep a copy in your password manager.** Losing it means encrypted data can't be read.
   * `SENTRY_DSN`: optional now (leave empty), recommended before pilots.
   * `CORS_ALLOWED_ORIGINS` on the API: `https://homesika-staging-web.onrender.com`.
   * `VITE_API_URL` on the web site: `https://homesika-staging-api.onrender.com`.
   * `DJANGO_SECRET_KEY` is generated by Render automatically.
   * `PAYSTACK_SECRET_KEY`, `FLUTTERWAVE_SECRET_KEY`, `FLUTTERWAVE_WEBHOOK_HASH`, `TERMII_API_KEY`:
     leave empty at first. Staging starts with the **mock** gateway and mock SMS (nothing real is
     charged or sent). When you have **test** keys, paste them in Render (never in chat or GitHub),
     then change `PAYMENT_GATEWAYS` to `paystack,flutterwave` in the `homesika-staging-shared` group.
   * Webhook URLs to enter in the gateway dashboards:
     `https://homesika-staging-api.onrender.com/webhooks/payments/paystack/` and
     `.../webhooks/payments/flutterwave/`.
5. Click **Apply**. The first build takes a few minutes. On every deploy, the API runs
   `migrate` before taking traffic.
6. **Check it:** open `https://homesika-staging-api.onrender.com/health/ready`. You should see
   `{"status": "ok", ...}`.
7. **Create your admin user:** open the API service → **Shell**, then run
   `python manage.py createsuperuser`.

## Phase 2: WhatsApp, the assistant and photos

Do these when you're ready; until then staging uses the mock WhatsApp and mock assistant.

1. **Photos (do first; listings need them).** Create a Cloudflare R2 bucket (or S3), make it public
   (or attach a custom domain), and create an API token with read/write access to it. Then set
   `S3_BUCKET`, `S3_ENDPOINT_URL` (R2: `https://<account-id>.r2.cloudflarestorage.com`),
   `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` and `S3_PUBLIC_DOMAIN` (the public bucket domain).
2. **Claude.** In the Anthropic Console, create an API key for a "homesika-staging" workspace and set a
   monthly spend limit there too.
   * Paste the key as `ANTHROPIC_API_KEY` in Render (never in chat or GitHub).
   * Set `ASSISTANT_PROVIDER` to `anthropic`.
   * Run the evaluation once from the API service's **Shell**:
     `python manage.py assistant_eval --limit 10 --yes`, then the full set (it costs money; the
     command shows the estimated cost).
3. **WhatsApp.**
   * In Meta Business Manager, create the WhatsApp Business account and add the Homesika number.
   * In the Meta developer app, add the **webhook**:
     * URL: `https://homesika-staging-api.onrender.com/webhooks/whatsapp/`
     * Verify token: any long random string; put the same value in `WHATSAPP_VERIFY_TOKEN`.
     * Subscribe to the **messages** field.
   * Set these in Render:
     * `WHATSAPP_PHONE_NUMBER_ID`;
     * a permanent `WHATSAPP_ACCESS_TOKEN` (system user token);
     * `WHATSAPP_APP_SECRET` (App settings → Basic);
     * `SUPPORT_PHONE`;
     * `WHATSAPP_PROVIDER` = `cloud`.
   * Submit the templates in `docs/WHATSAPP_TEMPLATES.md`, and list each one in `WHATSAPP_TEMPLATES`
     once approved.
   * `TODO(verify)`: menu names in Meta's dashboards change often; follow Meta's current "Cloud API
     get started" guide.

## Phase 3: bills (airtime, data, TV, electricity)

Staging starts with the **mock** bill provider: nothing real is bought.

1. **Fund the VTU.ng wallet.** This is Homesika's own float with the provider; customers never hold
   a balance with us.
2. **Set the VTU.ng credentials in Render:**
   * `VTUNG_USERNAME`, `VTUNG_PASSWORD`;
   * `VTUNG_USER_PIN` (the PIN VTU.ng signs webhooks with);
   * the webhook URL in VTU.ng's dashboard:
     `https://homesika-staging-api.onrender.com/webhooks/bills/vtung/`.
3. **Load the live catalogue.** In the API service's Shell, run
   `python manage.py sync_bills_catalogue`. This loads data bundles and TV bouquets with prices.
   Run it again weekly; it's safe to repeat.
4. **Set `BILLS_PROVIDERS`** to `vtung`. Add `,flutterwave` only after you've entered Flutterwave
   bill codes for each biller in the admin (Bills → Billers → provider codes).
5. **Fees and limits (defaults already set):** NGN 100 per order on electricity and cable TV, nothing
   on airtime and data, and no daily spending limit. To change them, set `BILLS_FEES` (kobo, e.g.
   `{"electricity": 10000, "cable_tv": 10000}`) or `BILLS_DAILY_LIMIT` (kobo; `0` = no limit).
   **Fund the VTU.ng wallet before switching `BILLS_PROVIDERS` to `vtung`.** With no balance, every
   order is refunded.
6. **Watch the admin:** orders flagged **needs review** are payments we couldn't settle
   automatically (wrong amount, or no final status from the provider). Check them daily.

## Phase 4: repairs and artisans

1. **Create a private bucket** for repair photos and ID documents, with **no public access** (for
   example a second Cloudflare R2 bucket), and set `S3_PRIVATE_BUCKET`. Without it the deploy check
   warns, and private files go to the photo bucket under `private/`. The app only ever hands out
   15-minute links to them.
2. **ID checks (automatic):** `ID_VERIFICATION_PROVIDER=nin` checks the NIN with `NIN_PROVIDER` and
   has the photo of the NIN slip or card read by AI (`ASSISTANT_PROVIDER=anthropic` and an
   `ANTHROPIC_API_KEY` are needed for real reading). Staging can use `NIN_PROVIDER=mock`; production
   refuses it until a real provider adapter is added. Until then, production can run with
   `ID_VERIFICATION_PROVIDER=manual`, where staff review everything in the admin.
   **Switching on Smile ID:**
   1. Sign up at portal.usesmileid.com and get the **sandbox** partner ID and API key.
   2. Put them in `backend/.env` (`SMILEID_PARTNER_ID`, `SMILEID_API_KEY`, `SMILEID_PRODUCTION=false`).
   3. Run `docker compose exec api python manage.py smileid_check <a sandbox test NIN>` and send me the
      printed shape (it hides every value). I'll confirm the field names, then you set
      `NIN_PROVIDER=smileid` on staging.
   4. For live, use the production keys with `SMILEID_PRODUCTION=true`.
3. **Addresses (automatic):** an address passes when it's the same place as the NIN record's address,
   or from a proof of address (bill, statement or tenancy paper, last 3 months) read by AI. Anything
   unclear, and anything an artisan asks a person to look at, appears in the admin under
   **Artisans → Verification checks**, filtered by *Waiting for a person to review*. Open the photo,
   read "What the automatic check found", and choose **Passed** or **Failed** (type a reason in
   *Note*). ID and address photos are deleted 90 days after the check passes
   (`ARTISAN_DOCUMENT_RETENTION_DAYS`).
4. **Guarantor links** are sent by SMS and open `WEB_APP_URL/v/<token>`, so `WEB_APP_URL` must be
   the public web address.
5. **Background jobs:** `artisans-housekeeping` (hourly) retries checks stuck while a provider or
   the model was down, and deletes old photos. `maintenance-housekeeping` runs every 30 minutes on the worker. It expires
   job offers nobody answered (24 hours), reminds tenants to confirm (after 2 days), and confirms
   repairs automatically after 7 days.

**Privacy notice:** it's served at `WEB_APP_URL/privacy`. Set `EXPO_PUBLIC_PRIVACY_URL` to that address
when you build the app, so sign-up links to it. The text is a **draft for legal review**
(`docs/PRIVACY_NOTICE.md`).

## Phase 5: estates, gate passes and panic alerts

1. **The alerts worker:** the blueprint now has `homesika-staging-alerts`, a Celery worker for the
   `alerts` queue only. Panic alerts never wait behind reminders. It also runs the every-minute
   delivery check (push receipts and SMS fallback). **Sync the blueprint** in Render (Blueprints →
   your blueprint → *Sync*). Without this worker, alerts reach the security desk screen but no
   push or SMS goes out.
2. **Push (Expo):**
   1. In `mobile/`, run `npx eas init`. It creates the EAS project and writes its id into
      `app.json` (`extra.eas.projectId`, empty now). Without it the app skips push registration
      and people get SMS instead.
   2. Add the Android FCM credentials and the iOS APNs key: `npx eas credentials`.
   3. Optional: turn on *enhanced push security* in your Expo account and put the token in Render
      as `EXPO_ACCESS_TOKEN`. Never paste it in chat or `.env.example`.
   4. Staging and production use `PUSH_PROVIDER=expo` (already in the blueprint). Production
      refuses the mock.
3. **WebSockets:** the live security desk uses `wss://<api host>/ws/estates/<id>/desk/`. The API
   already runs on Daphne (ASGI), so nothing to add. `CORS_ALLOWED_ORIGINS` must include the web
   app's address, because the socket checks it.
4. **Mobile build settings:** set `EXPO_PUBLIC_WEB_URL` to the web app's address, so a guard can
   open the desk from an alert push.
5. **Settings you can change** (Render → API → Environment):
   `PANIC_PUSH_FALLBACK_SECONDS` (45: SMS if a push isn't confirmed in time),
   `PANIC_SMS_STAFF_ALWAYS` (true: staff get SMS and push), `PANIC_MAX_PER_HOUR` (5),
   `ANNOUNCEMENT_SMS_FALLBACK` (true).
6. **First test in a real estate:** add the estate, add a guard as *Security desk* in Team, open
   **Security desk** on a screen at the gate, and press **Send a test alert**. The alert detail
   shows who got it and how fast. Repeat it with phones in battery saver.
7. **WhatsApp:** optional new template `dues_reminder` (`docs/WHATSAPP_TEMPLATES.md`). Until it's
   approved, dues reminders go by SMS.

## Every later release

Just push to `main`. Render redeploys automatically; CI on GitHub runs the tests in parallel.
To stop broken builds from deploying, you can turn on "deploy only when CI passes" later (Render
calls this *auto-deploy after checks pass*; `TODO(verify)` the exact setting name).

## Good to know

* **Plans and cost:** background workers, Key Value and the always-on web service need paid
  plans. The names in `render.yaml` (`starter`, `basic-256mb`) are placeholders to check against
  your dashboard. See render.com/pricing. Free Postgres instances expire after a limited time,
  so don't use one for real data.
* **Region:** `frankfurt` is set because it's the closest Render region to Nigeria that I know
  of. Change it if Render now offers something closer.
* **Files:** Render's disks are wiped on every deploy, so nothing important is stored on them.
  Receipts are generated on request. Tenant photos and documents (later phases) go to S3-compatible
  object storage (e.g. Cloudflare R2), which we set up when the first upload feature ships.
* **Secrets:** they live only in Render (and your password manager), never in GitHub.
* **Production:** duplicate `render.yaml`'s services with `-prod` names (or use Render's
  environments feature), live provider keys, `config.settings.production` and a custom domain
  (`api.homesika.com`, `app.homesika.com`).

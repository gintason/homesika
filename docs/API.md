# Homesika: API outline

> **The exact contract is `docs/openapi.yaml`**, generated from the code (`python manage.py spectacular
> --file ../docs/openapi.yaml`); CI fails if it is out of date. This page explains the conventions and
> the plan for later phases.

Base path: `/api/v1`. The API is JSON over HTTPS. The OpenAPI schema is generated by
drf-spectacular at `/api/v1/schema/`, with docs at `/api/v1/docs/` (non-production only).

## Conventions

* **Auth:** send `Authorization: Bearer <access JWT>`. Access tokens live about 10 minutes;
  refresh tokens rotate and are blacklisted on use.
* **Org context:** staff endpoints are nested under `/orgs/{org_id}/…`. Membership and role are
  checked on every request, and an object outside the org returns **404** (never 403, so object
  existence doesn't leak).
* **Self-service endpoints** (tenant, resident, artisan) live under `/me/…` and return only
  the caller's own data.
* **Money** goes out as strings in major units (`"150000.00"`) with `currency`. It comes in the
  same way, and is stored as integer kobo.
* **Idempotency:** requests that create money movement or records (`payments/manual`,
  `payment-links`, `me/pay`, `charges`, `expenses`, `settlement-accounts`) accept an
  `Idempotency-Key` header (16–64 characters). A retry with the same key and body returns the
  original response with `Idempotent-Replayed: true`; the same key with another body gets 422;
  a retry while the first is running gets 409. Optional in Phase 1 (our clients always send it);
  it becomes required before third-party API access opens.
* **Errors:** always the same envelope.
  `{"error": {"code": "<stable_code>", "message": "<localised>", "details": {…}}}`
  The language follows `Accept-Language` (`en`, `pcm`, later `fr`).
* **Pagination:** cursor-based (`?cursor=`); default 20 items, maximum 100.
* **Filtering and search:** `?status=`, `?property=`, `?q=` where documented.
* **Rate limits:** per IP and per user scopes; `429` comes with `Retry-After`.
* **Caching:** `ETag` on read-heavy GETs, for weak networks.

## Auth and account [Phase 1]

| Method | Path | Purpose |
|---|---|---|
| POST | `/auth/register/` | Start sign-up (name, phone, email) → OTP challenge |
| POST | `/auth/otp/resend/` | Resend, or switch SMS → email |
| POST | `/auth/otp/verify/` | Verify code → `create_pin` or signed-in |
| POST | `/auth/pin/setup/` | Create 6-digit login PIN, bind device |
| POST | `/auth/pin-login/` | Everyday login: device + PIN |
| POST | `/auth/login/` | New device: phone/email + PIN → OTP |
| POST | `/auth/pin/forgot/` | Reset PIN via OTP (signs out other devices) |
| POST | `/auth/refresh/`, `/auth/logout/` | Token rotation, sign out |
| GET/PATCH | `/me/` | Profile, language |
| POST | `/me/transaction-pin/` | Set/change 4-digit transaction PIN |
| GET/POST | `/me/consents/` | View/grant/withdraw consents |
| POST | `/me/data-requests/` | Export or delete my data (NDPA) |
| GET/POST/DELETE | `/me/devices/`, `/me/push-tokens/` | Device management, push registration |

## Webhooks (no auth header; signature-verified, idempotent)

| Path | Source | Verification |
|---|---|---|
| `/webhooks/paystack/` | Paystack | HMAC signature header, `TODO(verify)` against current docs |
| `/webhooks/flutterwave/` | Flutterwave | Secret hash header, `TODO(verify)` |
| `/webhooks/whatsapp/` (GET verify, POST events) | Meta | Verify-token challenge + payload signature, `TODO(verify)` |
| `/webhooks/vtu/{provider}/` | VTU providers | Per provider, `TODO(verify)` |
| `/webhooks/sms/{provider}/` | SMS delivery reports | Per provider, `TODO(verify)` |

Every webhook is stored first (unique by provider event id), acknowledged fast with a 200, and
processed by Celery. Payments are re-verified with the gateway API before they count.

## Health

* `GET /health/live`: the process is up.
* `GET /health/ready`: the database and Redis are reachable. Returns 503 otherwise.
